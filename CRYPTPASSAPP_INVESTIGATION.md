## Unlock flow

1. `Config.readData()` reads the configured vault and recovery sequence.
2. `CryptPassCached` is constructed from those objects.
3. `GetK(password)` reconstructs the master key. A `false` result takes the ordinary wrong-password path.
4. If `GetK()` returns a key, `GetEntriesManage(key, true)` synchronously decrypts and parses `Pass.Entries`.
5. Errors during load, reader construction, key derivation, or entry decryption now produce `UNLOCK_DIAG|{...}`. The diagnostic includes stage, format/KDF metadata, entry-envelope metadata, error category/type, and a small allowlist of safe library error messages. It deliberately excludes password, master key, recovery sequence values, and decrypted entries.

For format v2, successful `GetK()` authenticates/decrypts the password-wrapped master key; the entries envelope is a separate authenticated-decryption step. For legacy format, successful `GetK()` alone cannot reliably prove the password and sequence are correct.

Previously the details were prepended to a native `alert()`. During the first attempted diagnostic build in this task, TypeScript was invoked with `--noEmit`: this checked the TypeScript but left `www/js/cryptpassapp.js` unchanged, so Cordova packaged stale UI code. This is the **PROVATO** reason the first APK had no diagnostic panel/button. The final build uses emitting `npx tsc`, and its APK assets include the updated UI.

A local Node round-trip used the installed CryptPass code and an in-memory writer:

## SAF / Android permissions

**PROVATO dal codice:**

- Folder selection requests read, write, prefix, and persistable URI grant flags.
- The result handler takes the persisted read/write flags and verifies both persisted permissions.
- New-vault creation checks persisted read/write permission again before creating the document.
- Existing vaults selected from a granted folder are represented by a stable tree URI plus relative filename; the app resolves the current child by filename before each read/write.

**NON DIMOSTRATO sul dispositivo:**

- Whether Android or a particular provider later revokes either permission for this vault.
- Whether the actual persisted URI still has both read and write permissions after process death/reboot.
- Which DocumentsProvider serves the failing folder.

The implementation checks the grant at folder selection and creation, but does not currently collect a permission snapshot for every later read/write. The user has since confirmed that the folder grant remains usable for subsequent writes; the suspected grant loss was not the cause of the unlock failure.

## Read/write byte comparison

**PROVATO dal codice:**

- New-file creation writes UTF-8 bytes via `ContentResolver.openOutputStream(..., "wt")`, closes the stream, then the app reads the document back and compares the returned text with the submitted JSON (after trimming trailing whitespace).
- Subsequent writes call SaveDialog on the resolved document URI, then read back and compare text (also allowing trailing whitespace).
- This is stronger than treating `OutputStream.write()` as success, but the comparison is not recorded in a diagnostic and no SHA-256/expected-vs-actual byte lengths are retained.

**NON DIMOSTRATO nel caso reale:** whether a particular write/read-back passed immediately before the failing unlock, and whether an external sync replacement occurred between those operations.

## Overwrite and URI replacement

Folder-mode writes resolve the current document from the persisted tree URI and filename, so an in-place replacement/new document ID from a sync provider can be followed on the next operation. SaveDialog then opens that resolved URI with mode `"wt"`. The actual provider's behavior for overwrite and document-ID replacement was not exercised.

## Async/concurrency analysis

The inspected Android writer has no per-URI serialization queue or write lock. The new-vault setup awaits sequence persistence and then keypass persistence in order. Ordinary save call sites await `SetEntries()`.

No overlapping writes were reproduced. A race remains **POSSIBLE but UNPROVEN** if distinct UI/actions invoke persistence concurrently; no `WRITE_START/WRITE_END` device trace exists to establish it.

## Findings

- **PROVATO:** The current local CryptPass v2 implementation can create, serialize, reopen, and decrypt a fresh empty vault outside Android.
- **PROVATO:** The source requests and verifies persisted read/write grants during folder selection and new-vault creation.
- **PROVATO:** Current app write paths perform a read-back text comparison after create and save.
- **PROVATO:** The first attempted diagnostic APK lacked the UI changes because compilation used `--noEmit`; this explains the user's report of no panel/button for that APK.
- **PROBABILE:** The earlier diagnostic-before-this-task may also have been hard to see because it was only in a native alert; its device behavior was not captured.
- **NON DIMOSTRATO:** Android removes the write grant after a first write.
- **NON DIMOSTRATO:** The current user's vault bytes match the payload generated before storage, or that current Android CryptPass receives the same recovery sequence and file as the successful local harness.
- **NON DIMOSTRATO:** A specific SAF provider, write race, or CryptPass bug causes the reported failure.

## Root cause

**PROVATO — the reported `_a.scheduleLock is not a function` is an application bug after vault decryption, not a SAF grant failure.** `AutoLock.reset` was a static arrow-property callback. Because all app classes are emitted into one TypeScript `outFile`, the generated callback referred to the temporary alias `_a`; TypeScript later reused `_a` for another class (`Config`). On successful unlock, `AutoLock.start()` invoked the callback, which then tried to call `Config.scheduleLock` and threw. The UI caught that exception in the unlock flow and showed the same generic “entries cannot be read” message, even though `GetK()` and `GetEntriesManage()` had succeeded. The fix converts timer/event callbacks to static methods that reference `AutoLock` directly, avoiding the shared alias. The generated JavaScript inside the final APK was inspected: `AutoLock.reset()` and `AutoLock.scheduleLock()` are methods, and there is no `_a.scheduleLock` reference.

The earlier diagnostic panel was also absent from the first APK in this task because that build used `tsc --noEmit`. The final builds now emit the JavaScript before Cordova packages it.

This explains the reported unlock failure. The SAF write-grant theory was not the cause. The user subsequently confirmed that repeated writes work and that the folder grant remains available. The temporary leading-space write probe has now been removed completely.

## Patch

- Added structured, secret-free diagnostics across vault load, reader construction, key derivation, and entries decryption.
- Added a persistent diagnostic panel with an explicit clipboard button; copy uses Cordova Clipboard on Android and the Web Clipboard API where available.
- Removed the temporary leading-space write probe after the user confirmed that Android retains the folder grant and repeated writes succeed. No unlock path now modifies the vault as a diagnostic.
- Updated README's dependency note: `package.json` selects the default Git branch while `package-lock.json` records the exact commit for reproducible installs.
- The first debug APK produced in this investigation accidentally contained stale compiled UI because of `tsc --noEmit`; it was missing the panel. This was found after the user's device report.
- Regenerated the final debug APK at `platforms/android/app/build/outputs/apk/debug/app-debug.apk` using the side-by-side test-package procedure, with emitting `npx tsc`; `config.xml` was restored after the build. The final APK was rebuilt again after the AutoLock fix and includes the corrected methods.
